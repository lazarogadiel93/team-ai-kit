El problema real

Cada dev configura su AI por su cuenta

Hoy no hay estándar. Cada dev tiene su asistente de AI configurado diferente. Las convenciones del equipo no llegan al AI, y el conocimiento se pierde al cerrar cada sesión.

✗ Sin estandarizar

  • El AI de cada dev sigue convenciones diferentes
  • Lo que un dev aprende en una sesión se pierde al cerrarla
  • Cada nuevo integrante arranca de cero con su AI
  • Las decisiones arquitectónicas no llegan al asistente
  • El AI genera código que no sigue los patrones del equipo

✓ Con Team AI Kit

  • Skills y reglas por rol, iguales para todos
  • Memoria compartida: lo que aprende un dev, lo sabe el equipo
  • Onboarding de 2 minutos: un comando y listo
  • Convenciones del equipo inyectadas automáticamente
  • Updates que nunca pisan las customizaciones locales
Beneficios concretos

Qué recibe cada rol

Cada rol tiene skills y reglas específicas. Estos son ejemplos reales de cómo cambia el comportamiento del AI cuando el equipo está estandarizado.

Frontend

React / Next.js

  • TypeScript estricto: cero any, tipos de retorno explícitos
  • Server Components por defecto en Next.js, use client solo cuando es necesario
  • Cada feature es un módulo cerrado, sin imports cruzados entre features
  • Componentes presentacionales puros, lógica de negocio en hooks/services
  • Validación con Zod, schemas co-localizados con la feature

Backend Node.js

API Design / Testing

  • Separación en capas: routes → controllers → services → repositories
  • Validación con Zod en el borde de entrada, no dispersa
  • Error handling centralizado con clases tipadas
  • Inyección de dependencias para facilitar testing
  • Secrets y configs siempre vía variables de entorno
Sin estandarizar

Con Team AI Kit
// Controller: valida y delega
async getById(req: Request, res: Response) {
  const { id } = userIdSchema.parse(req.params);
  const user = await this.service.getById(id);

}

// Service: lógica de negocio
async getById(id: string): Promise<User> {
  const user = await this.repo.findById(id);
  if (!user) throw new NotFoundError('User');

DevOps

CI/CD / Contenedores / Observabilidad

  • Pipelines con etapas claras: lint → test → build → deploy, con fail-fast entre stages
  • Dockerfiles multi-stage, imagen base con versión explícita, usuario non-root, health check
  • Secrets nunca en el repo — variable groups, Key Vault o env vars del CI
  • Logging estructurado (JSON) con request ID para trazabilidad end-to-end
  • Métricas RED (Rate, Errors, Duration) como estándar de observabilidad
  • Dry-run / plan antes de apply en producción, cambios reversibles siempre
Dockerfile sin estandarizar
# Sin multi-stage, root, sin health check
FROM node:latest
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["npm", "start"]

# Imagen pesada, no reproducible,
# corre como root, sin health check
Dockerfile con Team AI Kit
# Multi-stage, versión fija, non-root
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

FROM node:20-alpine AS runtime
RUN adduser -u 1001 -D appuser
COPY --from=builder /app/dist ./dist
USER appuser
HEALTHCHECK CMD wget -qO- localhost:3000/health
CMD ["node", "dist/index.js"]
Pipeline sin estandarizar
# Sin stages, sin fail-fast, secret hardcoded
trigger: [main]
steps:
  - script: npm test
  - script: docker build -t app:latest .
  - script: docker push app:latest
    env:
      REGISTRY_PASS: 's3cret123'  # en el repo
Pipeline con Team AI Kit
stages:
  - stage: Validate  # lint + test
    jobs:
      - script: npm run lint
      - script: npm test -- --coverage

  - stage: Build
    dependsOn: Validate  # fail-fast
    jobs:
      - script: docker build -t app:$(Build.BuildId) .

  - stage: Deploy
    condition: succeeded()
    variables:
      - group: production-secrets  # Key Vault
QA / Analistas Funcionales

Análisis estructurado / Debug / Investigación

  • Skills de thinking y debug cargados automáticamente — el AI no salta a soluciones
  • Descomposición del problema antes de proponer: ¿cuál es el problema real? ¿qué supuestos hay?
  • Root cause analysis sistemático: aislar capa → función → input → causa raíz
  • Investigaciones de bugs guardadas en engram para futuras sesiones y otros miembros
  • Análisis de impacto: el AI evalúa riesgos y blast radius antes de proponer cambios

Engram en acción para funcionales

El analista investiga el incidente y documenta: causa raíz (pool de conexiones), solución aplicada (pool size dinámico), y precauciones. engram guarda todo automáticamente. Semanas después, otro analista reporta síntomas similares en otro servicio — el AI ya conoce el patrón y sugiere verificar el pool de conexiones antes de que escale.

Tech Lead / Arquitecto

  • Los nuevos integrantes se onboardean en 2 minutos: team-ai-kit setup y tienen todo configurado
  • Consistencia garantizada: todos los devs reciben los mismos patrones y convenciones sin esfuerzo

Profundización

Team Knowledge Repo

Un repositorio Git centralizado donde el Tech Lead define los skills, reglas y convenciones que todo el equipo recibe automáticamente. Es el cerebro compartido del equipo.

Cómo funciona

1

Tech Lead configura el repo

Crea skills y reglas que reflejan las convenciones del equipo. Ejemplo: cómo nombrar endpoints, qué logger usar, patrones de testing.

2

Dev hace setup con el repo

team-ai-kit setup --team-repo https://dev.azure.com/equipo/knowledge
Los skills y reglas del equipo se descargan y se inyectan en el AI del dev.

3

Updates sin romper nada

team-ai-kit update — Pull del repo del equipo. Los skills nuevos se agregan, los actualizados se aplican, pero lo que el dev customizó localmente nunca se pisa.

4

Nuevo integrante = 2 minutos

Un dev nuevo corre team-ai-kit setup, elige su rol, apunta al team repo, y tiene toda la configuración del equipo sin leer documentación.

Prioridad de merge

Cuando corrés team-ai-kit update, las capas se resuelven así — lo local siempre gana.

Customizaciones locales del dev
Skills o reglas que el dev modificó personalmente
Prioridad máxima — nunca se pisa
Team Knowledge Repo
Skills y reglas definidos por el Tech Lead
Se agregan si son nuevos, se actualizan si no fueron modificados
Defaults del package
Skills base incluidos en team-ai-kit
Base — menor prioridad

El tracking se hace con hashes SHA256. Si el dev no tocó un archivo, se actualiza. Si lo personalizó, se respeta.

Ejemplo real: estandarizar logging en el equipo

1

El Tech Lead detecta un problema

Cada dev loguea diferente: unos usan console.log, otros pino, otros winston. Los logs de producción son imposibles de parsear.

2

Crea un skill en el Team Knowledge Repo

Agrega skills/shared/logging/SKILL.md con las reglas: pino como logger, JSON estructurado, request ID obligatorio, nunca loguear datos sensibles.

3

Pushea al repo y avisa al equipo

Los devs corren team-ai-kit update (o se actualiza automáticamente). El nuevo skill se instala en todos.

4

Resultado

A partir de ahora, cuando cualquier dev del equipo escribe código que involucra logging, el AI automáticamente aplica pino, JSON estructurado, y request ID. Sin que el dev tenga que recordarlo.

Lo mismo aplica para cualquier estándar del equipo

Convenciones de naming, patrones de error handling, estructura de endpoints, reglas de testing, configuración de pipelines, manejo de secrets — todo lo que el equipo quiera estandarizar se documenta como skill o regla en el Team Knowledge Repo, y el AI de cada dev lo aplica automáticamente.

Dependencia

gentle-ai

La base sobre la que Team AI Kit se construye. Open source, mantenido por Gentleman Programming.

gentle-ai configura tu entorno de AI (VS Code + Copilot, IntelliJ, OpenCode) con:

  • Skills — instrucciones que el AI carga automáticamente según el contexto (ej: cuando detecta un bug, carga el skill de debug)
  • MCP Servers — herramientas externas que el AI puede usar (documentación actualizada vía Context7, etc.)
  • Instrucciones personalizadas — reglas inyectadas directamente en el AI

gentle-ai es para el dev individual. Team AI Kit extiende gentle-ai para equipos: agrega roles, skills compartidos, team knowledge repos, engram sync, y merge inteligente.

Punto clave

engram — La memoria del equipo

Este es el diferencial más importante. Sin esto, cada sesión de AI empieza de cero.

El problema sin memoria

Imaginemos que cada vez que usamos una calculadora, tenemos que cargar los números de nuevo. No hay memoria, no hay historial. Eso es exactamente lo que pasa hoy con los asistentes de AI: cada sesión empieza en blanco. El dev explica el contexto, el AI trabaja, y al cerrar — todo desaparece.

Qué resuelve engram

1

Memoria individual

El AI recuerda tus decisiones, bugs que resolviste, patrones que estableciste. Entre sesiones. Sin que hagas nada manual.

2

Memoria compartida

Lo que aprende un dev se sincroniza con el equipo vía git. Git hooks automáticos (pre-commit + post-merge) se encargan de todo.

3

Conocimiento acumulado

Con el tiempo, el equipo construye una base de conocimiento que el AI de cada dev puede consultar. Decisiones arquitectónicas, root causes, gotchas.

Cómo fluye la información

Automático, vía git hooks. El dev no tiene que hacer nada.

Ejemplo real

Dev A investiga un bug de producción. Descubre que es una race condition en el cache de Redis. Documenta la causa raíz, la solución, y las precauciones. engram lo guarda automáticamente.

Semanas después, Dev B trabaja en otro servicio que usa el mismo patrón de cache. Su AI ya sabe del problema anterior y le advierte sobre la race condition antes de que ocurra.

Requiere atención

Instalación en entornos corporativos

La herramienta está lista. El único bloqueo es una restricción de seguridad en nuestras PCs que impide la instalación estándar.

El problema técnico

1

PowerShell Constrained Language Mode (CLM)

Nuestras PCs tienen CLM activado por política de grupo (GPO/AppLocker). Esto es una restricción de seguridad que limita qué puede ejecutar PowerShell.

2

Scoop bloqueado

Scoop es el package manager de Windows que usamos para distribuir la herramienta. CLM lo bloquea completamente porque depende de llamadas .NET que están restringidas.

3

Llamadas .NET restringidas

CLM bloquea llamadas como [Net.ServicePointManager]::SecurityProtocol y [Environment]::SetEnvironmentVariable, necesarias para descargar e instalar binarios.

Lo que ya hicimos

No estamos pidiendo que nos resuelvan el problema. Ya implementamos soluciones alternativas:

✓

Fallback de descarga directa

Si Scoop no está disponible, el setup descarga los binarios directo desde GitHub Releases sin usar Scoop.

✓

Compatibilidad con CLM

Reemplazamos todas las llamadas .NET bloqueadas con alternativas usando cmdlets de PowerShell nativos (registry cmdlets en lugar de [Environment]::).

✓

Instalación vía git clone

La alternativa actual es git clone + .\setup.ps1. Funciona si Git está permitido y la ejecución de scripts está habilitada.

Lo que necesitamos

Cualquiera de estas opciones desbloquea la adopción:

Opción A: Whitelist para el proyecto (ideal)

Agregar la carpeta de instalación a la whitelist de AppLocker/GPO para que los scripts de team-ai-kit puedan ejecutarse sin restricciones de CLM. Esto resuelve todo de una vez.

Opción B: Permitir ejecución desde una carpeta específica

Habilitar una carpeta designada (ej: C:\tools\) donde se pueda clonar y ejecutar scripts de PowerShell sin las restricciones de CLM. Mínimo impacto en seguridad.

Opción C: Acceso a GitHub para descarga de binarios

Asegurar que github.com y api.github.com no estén bloqueados, y que Invoke-WebRequest pueda descargar archivos. El setup se encarga del resto.

Nota

La herramienta es open source (licencia MIT), no requiere permisos de administrador para ejecutarse, y no modifica configuraciones del sistema. Solo necesita escribir archivos en el directorio del usuario (%LOCALAPPDATA% y %USERPROFILE%).
